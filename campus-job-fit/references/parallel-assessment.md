# 多 agent 全文评估

大量岗位推荐由主 agent 委派多个子 agent 同时评估。使用当前环境的子 agent 工具；并发数服从实际槽位、上下文容量和限流，主 agent 可同时处理独立批次。少量任务可串行。每个执行者必须自行读完 SKILL.md、assessment.md、ability-model.md，以及同一版本的完整画像和所分配岗位的职责、要求、招聘证据，按 v4 标准形成独立结论。不能用标题分类、模板评分或复制相似岗位结论替代阅读。

## 分配与独立写入

1. 先确认用户的实验批次／指定公司／全量选择并保存 `evaluation-scope.json`，再启动评估 agent。主 agent 固定本轮画像与已采集 JD 快照，分别记录全量与已选范围的可评估总数和已有有效评估数。并行期间不刷新快照或修改画像；用户改变输入时停止旧版本分配，按新版本流程处理。
2. 主 agent 调用 `next-batch` 取得待评估清单，按 `(company_id, job_id)` 分成互不重叠的批次。优先按公司分组，岗位特别多的公司再拆分；结合 JD 长度均衡任务，避免整家大公司占住一个执行者。批次大小以能够完整读取并可靠写出评估为准，不要求一岗启动一个 agent。
3. 在运行目录 `parallel/manifest.json` 保存批次 ID、执行者、岗位键列表、画像与 JD 指纹、输入输出路径、状态及起止时间。状态区分 pending、running、submitted、validated、failed；只有合并校验通过才记 validated。任务输入放在 `parallel/inputs/批次ID.json`，包含完整字段或可精确读取的快照路径。
4. 给每个子 agent 明确输入路径、负责的岗位键、评估标准路径和唯一输出路径。输出写到 `parallel/results/批次ID.json`，结构为 `{ "items": [{ "company_id": "真实公司ID", "assessment": { ...完整v4评估... } }] }`。子 agent 不写共享 `next-batch.json`、正式 `assessments` 文件或报告，不更改画像和采集快照。允许低匹配岗位简写理由，但仍须完整阅读并覆盖决定性要求。
5. 主 agent 是清单的唯一写入者。`next-batch` 没有领取或锁机制，不让多个执行者各自调用并领取相同结果。后续取批时排除 manifest 中尚在执行或等待合并的岗位；子 agent 完成后可继续领新批次，无须等待所有批次齐步结束。

现有 `next-batch --limit` 上限为 100，且没有 offset；它只限制读取大小，不能用来改变用户选择的评估范围。若当前返回的岗位都已分配，先回收并合并已完成批次，再取后续岗位，避免反复领取同一批。manifest 的初始总数来自已选范围的 `total_to_assess`，另存 `full_total_to_assess`，不能把单次返回数量当成本轮总量。

> 阅读给定 skill 及评估参考、完整画像和批次输入，只评估所分配岗位。逐岗读完 description、requirements、recruitment_evidence，输出符合 v4 的证据对照和四项 report_summary。使用输入中的当前指纹。仅写指定的独立结果文件；报告已完成岗位键、未完成项及原因。遇到输出截断继续读取，不凭标题推断，不自行派发额外岗位。

## 合并、质量检查与续跑

- 主 agent 核对结果岗位键属于其分配范围，且画像与 JD 指纹仍匹配。同一岗位出现多份或矛盾结论时回读并裁定，不能用最后写入者自动覆盖。脚本可检查、去重和序列化模型已完成的判断。
- 由主 agent 单独将结果按公司合并到 `assessments/公司ID.json`，保留其他批次和原有有效记录。同一 job_id 的有效重评替换旧条目，不追加重复项。合并后调用 `next-batch`，无效项按其具体原因返修；不能仅凭子 agent 声称完成或 JSON 格式正确就计入完成数。
- 检查各执行者的代表性结果，重点关注高能力、核心缺口与等级矛盾、资格不符、意愿无依据及不同执行者分档不一致。发现标准偏移时回读相关 JD 与画像，扩大复核或退回相关批次；抽查不能代替其余岗位的首次全文评估。
- 执行者失败或中断时保留已提交且验证通过的记录。确认旧执行者停止后再重新分配未完成岗位，给重试使用新的批次 ID 与输出路径，防止迟到结果覆盖。续跑先核对现有评估和分配状态，不重复派发仍在运行的岗位。
- 所有任务回收、有效评估覆盖用户已选范围、`next-batch` 的 `remaining=0` 后，执行不带 `--allow-partial` 的 `render`，核对 `complete_evaluation_scope`。实验或指定公司完成后先交付，不自动扩大范围；`full_remaining` 仍须披露。采集部分覆盖和待核实如实保留，不把所选范围完成说成全量完成或全来源采集完整。用户要求提前交付范围内尚未完成的结果时使用 `--allow-partial`。

## 运行时间

主 agent 在 `parallel/timing.json` 保存可核对的 ISO 起止时间（含时区）、实际并发上限、初始待评估数、本次新增有效评估数、剩余数和各阶段耗时。运行结束后写入最终状态；未完成时只报告已耗时。

- 评估墙钟时间：本次分批准备开始，到全部结果合并、返修和校验完成，包含任务调度与等待。
- 导出时间：单独记录 `render` 的开始、结束和耗时。
- 本次端到端时间：本次运行开始到最终交付文件生成。续跑复用既有采集时明确说明，历史采集时间单列，不算作本次重新执行。
- 中断后续跑：保留各执行区间，分别报告执行区间累计时间与首次启动至完成的总历时，说明暂停部分。

子 agent 耗时总和可作为额外统计，不能当作用户等待的墙钟时间。没有相同工作量的串行基准时，不宣称实际加速倍数；可依据已完成批次吞吐量给出带不确定性的剩余时间估计。

manifest、批次文件和 timing 是本操作约定的内部产物，由 agent 编排维护；现有 campus.mjs 不会自动生成它们，也没有新增并行评估 CLI 命令。
