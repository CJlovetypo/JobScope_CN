# 从历史链接到可验证修复

本文基于本仓库 2026-09-19 至 2026-09-21 的抓取与复核产物，于 2026-09-22 整理，未重新联网验证。维护资料的组织与恢复方式见 [历史库契约](history-dataset.md)。历史成功只证明当时的特定请求；未来必须重验。

## 证据顺序

同一公司的历史完整 JD 请求及主体复核 → 已验证的列表契约 → 官方页面实际跳转／公开配置 → 同主体跨届表格中的真实链接 → 聚合站或公告中的候选。顺序是调查优先级，不替代当前验证。失败记录有助于避免重走已知死路，但不是永久封禁名单。

从 `index/contracts.jsonl` 查询请求模板、完整 JD 样本、`source_file`、`result_file` 和旧状态；再查对应 `collections` 原始响应。三方链接只标记 `third_party_link_observed`。`registry_configuration_snapshot` 只表示正式库里存在该配置；完整能力应继续核对具体契约与样本，不能把所有记录升级成“抓取成功”。

## 按故障选操作

| 观察到的现象 | 优先检查和恢复方法 | 不能据此推出 |
| --- | --- | --- |
| 404/410、年度活动页消失 | 同公司历史门户、当前官网招聘跳转、同渠道公开菜单；比较稳定域名与变化的 project/activity/siteId | 年份加一或 ID 相邻就有效 |
| 页面开得了，JSON 结构变了 | 同站点实际前端请求、公开配置、懒加载职位模块；还原方法、请求体、分页与组织字段 | HTML 200 等于 API 可用 |
| 只剩单岗详情，列表正常 | 用原岗位 ID 在当前同租户列表核对；下架时保留历史详情并给公司列表入口 | 列表入口是原岗位的“新 URL” |
| 空列表 | 检查频道、日期、国家、过滤参数和列表结构；确认分页后标记当次空 | 公司不再招聘或租户必然失效 |
| 超时、DNS、429、403 | 限次重试网络错误；限流按冷却；登录／验证码停止参数探测 | 需要更换租户、暴力枚举或绕过限制 |
| 完整 JD 来自另一个雇主 | 对照官网、组织字段、子公司过滤；保留主体冲突 | 技术可抓取就可以替换 |
| 旧表说未准入，当前库已存在 | 按公司 ID、已核实别名和接口配置对账，注明已被哪次修复解决 | 旧失败状态仍代表当前结论 |

## 保留 URL 的语义

原始 URL 永不覆盖。用于查询的域名可转小写，查询参数、fragment、编码和路径大小写全部保留。`#/jobs`、`#/index?id=...`、`department[0]`、`queryId`、`orgCode`、`project`、`activity` 可能决定租户、频道或主体，不统一清洗删除。

实际跨届样本：腾讯同为 `join.qq.com/post.html`，2026 届样本多了 `activity`；字节跳动校园页的 `project` 在两份春招表不同；比亚迪既有带 hash 的专题也有招聘根域名。它们支持“入口结构分层检查”，不能证明两条 URL 是同一岗位或可互相替代。返回公司列表作为降级方案时明确它是列表。

## 平台线索

| 平台 | 历史链接中值得保留的部分 | 重验重点 |
| --- | --- | --- |
| Moka | host、orgId、siteId、campus/social 路径 | 从 init-data 或实际跳转获取项目，不猜 ID；同 orgId 也可能不同品牌；核对站点身份与频道 |
| 飞书招聘 | 租户域名、website-path、tenant ID（若原来有） | 同域公开配置可给新路径；自定义域名也可能使用飞书，不只依赖 URL 后缀分类 |
| 北森 | 租户域名、移动／桌面路径、jobAdId、网关 | 官网入口与同域前端脚本找新网关；有 LightBoltAPI 等不同契约；缺租户绑定时不采用 |
| Hotjob | 项目、公司域名、路由及实际组织参数 | 不能把 `wecruit.hotjob.cn` 这类公共主机当公司 ID；从配置和请求证实租户 |
| Workday | 实际 wd 主机、tenant、site、locale、外部岗位路径 | `myworkdaysite.com/recruiting/{tenant}/{site}` 保留原主机调用 CXS；新会话读 facets，地点 ID 不跨公司或跨时间硬套 |
| Oracle | host、sites/CX*、locationId、岗位 ID | 多站点可能同库存；全量唯一 ID 集合才能支持当次等价；缺中国筛选时查国家字段并保留分页限制 |
| Greenhouse／SmartRecruiters | board／company 标识、岗位 ID | 公共平台域名不代表雇主；用组织信息与官方反链确认租户 |
| AJINGA | company id、根公司与子频道 ID | `/django_rest/company/info/{id}/` 与列表行根公司核对；聚合站引用不是雇主归属证明 |
| Jobs2Web | 官方站点、CN 筛选、真实分页或 tile 加载请求 | 列表和 JD 能力独立；CN 返回值仍需核对大陆范围，不能忽略次要地点或总量 |
| 自研站／HCMCloud／51job | 公开前端请求、字段与传输策略、租户筛选 | 不将其他公司成功的请求体直接套用；签名与协议从当前公开客户端获得，缺材料标明阻塞 |

上表是本地样本归纳，不是平台永久 API 文档。具体参数以历史契约与当前实测为准。

## 公告、二维码和前端模块

WPS 超过一半的链接记录来自公众号文章。文章可能含真正投递链接、图片二维码或二跳入口；只扫描表格可点击对象会漏掉纯文本 URL。先查同一表格行的公告和投递列，读取实际内容后再跟进。二维码未解析要注明，不能标成“无 API”。

首页没有岗位 API 时，观察职位页面实际加载的模块及其明确引用的资源。历史上惠科和住建部平台的合同在懒加载资源里；UPM 的官网内容 API 后还有 Workday 官方跳转。记录请求预算、访问过的资源、未读范围；达到上限记 `discovery_truncated`，不能声称穷尽。

## 回归与留痕

针对变动平台运行相关已有测试；实际匿名请求验证主体、列表和详情。岗位 ID 稳定、详情正文和官方 URL 一致，分页是否完整另行报告。零岗位 API 和仅列表可以作为有用的维护结果，但不自动升级为原先要求的完整 JD 能力。

每次记录旧／新入口、旧／新契约、失败类型、候选来源、排除原因、身份依据、请求摘要、响应文件及 SHA256、检查时间和范围。采用变更后重新运行用户原查询；新抓取另开目录，保留旧结果。官方域名迁移或公司拆分无法确认时交付待核实结果，不猜定归属。
